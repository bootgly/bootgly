# `__Array` microbenchmarks

Study material for one recurring decision: **for a given array operation, is the
native call, a PHP built-in class, or a Bootgly abstraction the right choice?**

Results are committed, not just the code. Each run writes
`results/<case>.php-<version>.json` and renders them into
[`results/RESULTS.md`](results/RESULTS.md) — so the folder accumulates evidence
across PHP versions instead of forcing every question to be re-measured from zero.

> The stored numbers are a **starting point, not an answer**. They come from one
> machine under one workload. Re-run the case on your target runtime before you
> rely on it, and compare the runtime banners.

## Writing a case

A case file **returns a `Microbenchmark`** — it never measures on its own. A
microbenchmark is not a test and this API does not pretend to be one: a test
asserts one behaviour, while a benchmark *compares N implementations of the same
operation over a controlled input and attaches a decision to the result*.

```php
return new Microbenchmark(
   title: '...',
   inputs: ['sizes' => [5, 20, 100]],                // knobs, overridable from the CLI
   Gate: fn (array $inputs) => Workloads::check(),   // a faster wrong answer is not a result
   Comparisons: static function (array $inputs): array {
      $array = Arrays::build(Shapes::Sequence, $inputs['sizes'][0]);   // scoped here, leaks nowhere

      return [new Comparison(
         name: 'n = 20',
         Cases: [                                 // <- the measured code, and only it
            'native chain' => static fn () => Workloads::chain($array),
            'fused loop'   => static fn () => Workloads::fuse($array),
         ],
         baseline: 'native chain',                // explicit, not "whichever came first"
         recommendation: 'fused loop in hot paths',
         verdict: 'why',
      )];
   },
);
```

The harness is a framework entity — `Bootgly\ACI\Tests\Benchmark\Microbenchmark` — not a
copy in this folder. Any `<Entity>/tests/benchmarks/` gets it by declaring cases; nothing
is duplicated per directory. Case files are named `<name>.Microbenchmark.php` because
that is the entity they return.

Three things this shape buys:

- **Controllable input.** Sweeping a different size never means editing the
  file — and the resolved inputs are stored *with* the numbers, because a
  measurement without its input is ambiguous.
- **Reuse.** Shared inputs come from the framework's `Microbenchmark\Arrays`,
  shared operations live in `workloads.php`. Cases 4, 5, 7 and 9 compare the same
  `map → filter → materialize` work; implementing it four times would let them
  drift, and a benchmark whose implementations drift is measuring the drift.
- **Delimitation.** `Cases:` is unmistakably the benchmark; everything else is
  scaffolding.

## Running

```sh
bootgly test benchmark micro <dir>                        # every case, 5 processes each
bootgly test benchmark micro <dir>/4-chain-fusion.Microbenchmark.php
bootgly test benchmark micro <dir> --processes=9          # more processes = more confidence
bootgly test benchmark micro <dir>/4-chain-fusion.Microbenchmark.php --sizes=8,1000

bootgly test benchmark micro <case> --once   # single process — iterating, not committing
```

`RESULTS.md` is regenerated by the same command; there is no separate step.

**Always store results through the multi-process run.** A single process is not
trustworthy: PHP's tracing JIT does not make the same compilation decisions on
every run, so a case can come out consistently fast in one process and
consistently slow in the next — stable within each, bimodal across them.
Best-of-N rounds inside one process cannot see that. The command runs each case
in several fresh processes, keeps the best round per row, and records how far
the processes disagreed as `cross_process_spread`.

**Never measure code loaded from stdin.** Piping a script to `php` puts it outside
opcache, so the JIT never compiles it — while the native C functions it is being
compared against are unaffected. The same algorithm measured 3665 ns from a real file
and 10 870 ns from stdin (**2.97x**), and with `opcache.jit=disable` the two converge
to within 3%. A stdin measurement silently penalizes every userland candidate by
roughly 3x and will invert any userland-vs-native verdict. This trap produced a
retracted conclusion here once; the harness only ever loads real files, so it applies
to ad-hoc probes.

Measure on an **idle machine**. Two stability signals guard the numbers: rounds
within a process, and the spread across processes. A third guard marks rows
whose cost is not comfortably above the harness's own call floor (`floor_bound`):
those cannot be resolved by this method at all, and are excluded from the
stability verdict rather than reported as a wild ratio. When either exceeds 1.25x the
run says `UNSTABLE` and `RESULTS.md` flags the section. Do not read a verdict off
an unstable table — a single noisy run produced a fully inverted conclusion here
once, and a bimodal case later reported a wrapper beating the inline loop it
wraps. Both signals exist because of those two mistakes.

## The cases

| Case | Question it answers |
|---|---|
| `0-boundary` | Is `->First` / `->Last` worth it versus `array_key_first/last` + index? |
| `1-shape` | What does `->multidimensional` cost versus doing it inline? |
| `2-search` | When does `__Array::search()` earn its cost over `array_search()`? |
| `3-wrapper-forms` | What does *every* way of wrapping a native call cost — static method, property hook, magic `__get`, with and without construction? |
| `4-chain-fusion` | Fusing a chain into one pass: how much is there, and how much survives an abstraction? |
| `5-native-classes` | Do PHP's own C-implemented classes (generators, SPL iterators, `SplFixedArray`) beat the function chain? |
| `6-array-interfaces` | What do `ArrayAccess` / `Countable` / `Iterator` cost on an object versus the array it holds? |
| `7-pipeline-shapes` | Deciding the operation order once per chain instead of once per element — what is it worth? |
| `8-early-exit` | `find()` / `check()` against the native chain **and** against PHP 8.4's own `array_find()` / `array_any()`. |
| `9-pipeline-reuse` | Building the chain once and applying it per call — does it win at the sizes a hot path actually handles? |
| `10-terminals` | `count()` and `reduce()` — the terminals whose win comes purely from never materializing. |

## What the measurements established

**1. A single-operation wrapper can only cost.** Its floor is the native call it
hides plus the dispatch, so there is no faster implementation to "swap in". The
overhead is roughly constant, which means the *cheaper* the operation the worse
the ratio — `->list` over `array_is_list()` is the extreme case, because the
native call is only ~5 ns. Wrapping buys expressiveness, never speed.

**2. Chains are where the real money is, and it is paid twice.** The cost of
`array_values(array_filter(array_map(…)))` is the intermediate array materialized
between stages **plus** the per-element callback dispatch a C array function
performs (~37 ns, against ~19 ns for the same callback invoked from a
JIT-compiled userland loop). A single fused pass avoids both and takes roughly
**two thirds off**, at every size measured. The second half of that explanation
is why a userland loop can beat `array_find()` — see conclusion 5.

**3. PHP's built-in classes are a genuine third option, but not uniformly.**
Generators — C-implemented coroutines — beat the function chain by ~40-53% from
n≈20 up, and `SplFixedArray` by ~20-33%. SPL iterator *decorators*
(`CallbackFilterIterator`) lose badly (~2.6x), because they pay an object per
element. "Native" is not one thing; pick the mechanism, not the label.

**4. An abstraction beats the idiomatic chain and TIES the hand-written loop.**
`__Array\Pipeline` records the stages and runs them in one pass: ~3x faster than
the native chain from n=20 up, and within 2-4% of the same loop written out by
hand. Two conditions make that true, and dropping either loses it — the shape is
dispatched once per chain rather than once per element (worth 1.34-1.57x), and
the chain is built once rather than per call when the arrays are small.

> An earlier revision of this file claimed the abstraction "never catches the
> hand-written fused loop". That was measured against a naive op-loop
> implementation, and a later run that appeared to show the pipeline *beating*
> the hand loop by 6-18% was noise. Writing the same loop four ways — closure,
> named function, static method, method call — lands them all within 4%.

**5. A JIT-compiled userland loop dispatches callbacks cheaper than C does.**
PHP 8.4's `array_find()` / `array_any()` early-exit in C, yet `->find()` /
`->check()` still beat them by ~2x from n≈100 up, because the C function pays
full callback-dispatch per element. The native call only wins on a single filter
whose hit is a handful of elements from the front. "Native" is not automatically
faster — measure the dispatch, not the language it is written in.

## How to choose, in practice

- **Chained work** → `__Array`'s chain. It ties the fused `foreach` and reads as
  the chain it replaces. Build it once and `apply()` it when the arrays are small.
- **First match, or "is there one"** → `->find()` / `->check()`. This is the
  largest win in the folder — 3x to 52x — and it beats the native early-exit
  calls too.
- **Large or lazily-consumed results** → a generator pipeline; it avoids
  materializing at all and beats the chain comfortably.
- **A single operation** → call the native function directly. Reach for
  `__Array` when the `{key, value}` pair or a named shape check genuinely
  simplifies the caller — never for speed, and never constructing it per call.

## Why this folder is committed

Bootgly ignores `*.md` repository-wide. The local `.gitignore` re-includes this
README and `results/RESULTS.md` on purpose: the accumulated evidence is the
deliverable, and it has to survive a change of machine.

## Files

| File | Role |
|---|---|
| `*.Microbenchmark.php` | The cases — each returns a `Microbenchmark` |
| `workloads.php` | Operations specific to THIS study (+ the `Generic` prototype) |
| `results/` | Stored evidence, one JSON per case per PHP version, plus `RESULTS.md` |

The engine lives in the framework: `Bootgly/ACI/Tests/Benchmark/Microbenchmark.php` and
`Microbenchmark/{Arrays,Comparison,Results}.php`. The subject under measurement lives
in `Bootgly/ABI/Code/__Array.php` and `__Array/Pipeline.php`.
